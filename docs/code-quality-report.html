05发现分级

本轮无 P1 及以上新发现。以下 4 项 P2 为第一轮遗留（仍未处理），2 项 P3 为本轮新增微优化观察。

P2 · 测试

#1 resolveDroppedFile 缺 DataTransfer 形态矩阵测试

src/links-resolve.ts

该函数是拖拽解析的复杂度重心：text/plain、uri-list、自定义类型、JSON 载荷、files、dragManager 六条路径 + 各类容错分支。当前 links-resolve 语句覆盖仅 34.9%（分支 83.3%），矩阵测试是补齐的最短路径。与第一轮结论一致，仍未处理。

P2 · 测试

#2 UI 壳层缺 DOM stub 测试基建

src/features/*

features 层覆盖率 16.1%（view.ts 20.7%、view-toolbar 8.3%、view-context-menu 4.4%）。工具栏构建、右键菜单、拖拽/粘贴事件装配目前完全依赖手工验证。建立轻量 DOM stub（或 jsdom/happy-dom 环境）后，可先覆盖高价值交互：删除兜底（deleteActiveNode 强删路径）、粘贴事件豁免逻辑、窗口兜底判定。

P2 · 门禁

#3 vitest 未固化 coverage thresholds

vitest.config.ts

当前覆盖率无阈值门禁，核心域（domain/services/md-outline/md-serialize/file-lookup/concurrency）的覆盖回归不可见。建议对上述目录设置 thresholds（如 branches ≥ 85），UI 壳层单独排除，待 #2 落地后再逐步收紧。

P2 · 封装

#4 view.ts 仍保留 3 个可变 DOM 字段

src/features/view.ts L80-82

searchInput / searchCountEl / layoutSelect 仍由 view-search / view-toolbar 跨模块回填。已有 ViewDomContext 契约约束访问面（未列成员编译期拒绝），风险可控，但可写所有权仍散在视图类上。完整收口方向：builder 返回句柄由视图持有，或 view-* 内部自持、视图只读转发。

P3 · 性能（本轮新增）

#5 resolveDroppedFile 顶部 getFiles() 急切求值

src/links-resolve.ts L131

allFiles 仅在最后的 dataTransfer.files 兜底分支消费，但每次 drop 事件都先执行一次全库文件数组拷贝；text/plain / uri-list 命中时为纯浪费。拖拽是低频交互，影响极小；建议惰性化（移入该分支或用取值器）。同时顶部注释「一次拖拽多次解析，缓存文件列表」与实际消费点不符，可一并修正。

P3 · 性能（本轮新增）

#6 modal-image 预览每次按键重建 img

src/modal-image.ts L187-190

input 事件每次按键都 renderPreview() → preview.empty() + 新建 <img> 并重设 src，连续输入会反复触发资源重新加载。弹窗生命周期短、预览为本地资源，影响极小；可用「值未变短路 + 150ms 防抖」收口（concurrency.createDebouncer 现成）。

观察项（不计入发现）

  • 多图拖入逐张 Notice（view-dnd）：每张图片各弹一条通知，Obsidian 会自行堆叠排队，非缺陷；如介意可合并为计数式单条。
  • console.error 集中于错误路径：符合项目惯例（notifyError 管用户可见、console.error 管诊断详情）。
  • 竞态防护复核为优：view.ts 的 loadingFilePath 三重过期检查、EngineController 代际锁 + ResizeObserver、SavePipeline 循环排空 + pendingTree 兜底，均属于高质量防御设计，有对应测试或注释论证。
